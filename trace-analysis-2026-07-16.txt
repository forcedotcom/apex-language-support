RECOMMENDATIONS (Prioritized by Impact)
═══════════════════════════════════════════════════════════════════════════════

🎯 #1: PRE-LOAD STANDARD OBJECT SYMBOLS (Highest Impact)
───────────────────────────────────────────────────────────────────────────
Impact: ~400-600ms savings (10-15% of workspace load)
Effort: Medium

PROBLEM:
  Standard objects (contentDocumentLink, etc.) trigger 220ms IPC calls because:
  - They're not in cache initially
  - Each lookup goes through resourceLoader worker
  - IPC overhead is 730x the actual work

SOLUTION:
  Pre-load standard object symbol tables during worker initialization:
  
  a) Identify high-frequency standard objects (top 20-30)
  b) Load their symbol tables during resourceLoader.WorkerInit
  c) Populate cache before workspace load begins
  
  Alternative: Batch resolve operations to reduce IPC round-trips
  - Collect all needed FQNs during compilation
  - Single IPC call to resolve batch
  - 20 round-trips → 1 batch call = ~400ms savings

EVIDENCE:
  - 21 cache misses × 20ms average = 420ms
  - Worst case (contentDocumentLink): 220ms for single lookup
  - Worker actual work: <1ms per lookup
  - 91.7% hit rate means caching works, just starts cold


🎯 #2: IMPROVE SYMBOL TABLE CACHE HIT RATE
───────────────────────────────────────────────────────────────────────────
Impact: ~170ms savings
Effort: Low-Medium

PROBLEM:
  getSymbolTable has 14.3% cache hit rate (vs 91.7% for resolveClass)
  
SOLUTION:
  - Investigate why hit rate is so low
  - Are cache keys consistent?
  - Is cache being invalidated too aggressively?
  - Should symbol tables be pre-loaded like standard objects?


🎯 #3: BATCH/PIPELINE RESOLVECROSSFILE OPERATIONS
───────────────────────────────────────────────────────────────────────────
Impact: ~500-1000ms potential savings
Effort: High (architectural change)

PROBLEM:
  - Write-back takes 17x longer than compilation (2964ms vs 173ms)
  - resolveCrossFile is 95% of update.execute time
  - Operations are mostly sequential with small overlaps
  
SOLUTION:
  a) Batch cross-file resolution:
     - Collect all cross-file references per file
     - Resolve in parallel batches
     - Reduce IPC round-trips
     
  b) Pipeline compilation → write-back:
     - Don't wait for full write-back before next compile
     - Stream results to dataOwner
     - Allow parallel resolveCrossFile operations
     
  c) Speculative resolution:
     - Start resolving known standard objects before needed
     - Pre-warm cache based on file analysis


🎯 #4: REDUCE IPC OVERHEAD FOR COMMON OPERATIONS
───────────────────────────────────────────────────────────────────────────
Impact: ~200-400ms potential savings
Effort: Medium-High

PROBLEM:
  - Single resolveClass call: 220ms IPC vs 0.3ms actual work
  - 730x overhead is unacceptable
  
ROOT CAUSE INVESTIGATION NEEDED:
  - Is this Node.js worker_threads IPC overhead?
  - Is serialization/deserialization the bottleneck?
  - Are we sending too much data per IPC call?
  - Should we use SharedArrayBuffer for common lookups?
  
POTENTIAL SOLUTIONS:
  a) SharedArrayBuffer for FQN→symbol mapping
  b) In-memory cache in calling worker (duplicate cache)
  c) Batch IPC calls to reduce round-trips
  d) Profile IPC implementation to find bottleneck
